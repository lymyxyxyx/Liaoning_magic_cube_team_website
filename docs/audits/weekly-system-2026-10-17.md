# 周赛系统检查（2026-10-17）

范围：成绩录入/修订/删除、选手库保存、WCA 身份绑定、大堆榜编辑、PB 重算、导入及回滚、并发写入与权限。检查方式为代码追踪、线上只读聚合查询、单元测试，以及生产数据库中的独立临时 schema 测试。临时 schema 在测试后删除；未批量修补真实选手资料。

## 已确认的问题

### P1：修改一个选手会覆盖其他选手的较新资料（待修复）

`app/weekly/admin/weekly-player-library-console.tsx` 的 `saveEditingPlayer` 将被编辑选手替换进页面旧列表，然后 `savePlayers` 提交整个列表。`lib/weekly-player-library.ts` 的 `saveWeeklyPlayerLibrary` 对每一行无条件 upsert，未校验读取时的版本。

独立数据库复现：读取 A、B → 另一次操作将 B 的 PB 从 10 改为 9 并更新备注 → 旧页面只修改 A → B 的 PB 被写回 10，较新备注丢失。线上此入口包含 561 个选手档案；这代表潜在覆盖范围，不代表已发生 561 次错误。

建议：现有选手逐条提交修改，带版本检查；新增和停用独立处理。不能只在浏览器过滤变更而保留服务端无版本覆盖。

### P1：手动修改的个人 PB 会被下次重算覆盖（待修复）

`saveWeeklyPlayerLibrary` 只写 `personal_bests` / `personal_bests_average`。`lib/weekly-entry-store.ts` 的 `refreshWeeklyPlayerPersonalBest` 从 `personal_bests_base` / `personal_bests_average_base` 加周赛历史重新计算。手工改动没有进入作为重算依据的基线。

独立数据库复现：给无周赛成绩的选手手动保存三阶 PB=10 → 调用同一项目的 PB 重算 → PB 变为空。已有历史成绩时也可能被重算回旧值。线上 24 个有 PB 的档案没有非空单次基线，但其中可能是正常从周赛成绩推导的值，不能据此认定 24 个档案受损，更不能自动把现有派生 PB 全部写入基线。

建议：明确区分历史/手工基线和周赛推导成绩；手工调整基线需版本检查、修订记录，并在同一事务中重新计算。若要改差于真实历史成绩的 PB，应修改对应原始成绩，不能只覆盖展示值。

### P2：选手库“删除”成功不了，保存后记录回来（待修复）

`removePlayer` 仅把选手从 React 列表过滤掉；服务端保存只 upsert 提交的行，不删除或停用遗漏行，返回的全量列表又包含该选手。

独立数据库复现：提交 A、B → 再只提交 A → 返回数据仍有 B。应改为明确的停用操作并要求原因，保留历史成绩；不应把批量请求中遗漏的选手直接物理删除。

### P1：大堆自动匹配编号仍可能触发非预期身份写入（本次修复）

上次已解决自动匹配 WCA ID 被当作真实绑定提交的问题；本次发现 `weeklyNumber` 仍会从展示匹配结果自动发送，使只改数量也进入共享身份修改流程。若记录未绑定，而匹配到的选手有 WCA ID，空的记录 WCA 字段可能被解释为清除共享绑定。

改为明确列出保存字段，仅在用户实际编辑编号或 WCA ID 后提交身份修改字段；保存数量、性别、日期或备注不会提交自动推断的编号、WCA ID 或身份版本。新增两项请求构造测试。线上只读查询未发现当前满足上述清除条件的记录，因此未实施数据修补。
