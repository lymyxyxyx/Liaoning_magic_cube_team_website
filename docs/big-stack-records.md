## 首次上线

先应用数据库迁移：

```bash
npm run db:migrate
```

仓库内的权威基线是 `data/big-stack-baseline.json`，共 805 人，其中刘奕辰只保留 64。首次替换现有大堆数据有两种方式：

1. 登录周赛管理员账号后打开 `/weekly/big-stack?event=333`，选择“全量基线替换”，上传修正版 `.xlsx`，先预览再确认导入。
2. 在已配置 `DATABASE_URL` 的服务器执行：

```bash
npm run big-stack:baseline
```

两种方式都只替换三阶大堆榜，不影响二阶、金字塔、枫叶和镜面榜；操作在一个事务内完成，失败时会整体回滚。命令行导入固定校验 805 条唯一姓名和“刘奕辰 = 64”。

## 日常维护

后台默认使用“PB 合并”模式：

- 新选手会新增；
- 更高成绩会覆盖当前 PB，并留下历史；
- 相同或较低成绩会忽略；
- 缺席 Excel 的选手不会被删除；
- 优先按周赛选手 ID、WCA ID、唯一的完全同名匹配；
- 不做模糊匹配，未匹配或歧义记录交给管理员处理。

Excel 至少需要“姓名”和“最高记录”两列，也可以增加“周赛选手ID”“WCA ID”“达成日期”“备注”。后台还支持单条新增、修改、删除、搜索和最近修改历史。降低成绩、修改身份或删除时必须填写原因。

## 已知问题与后续建议

以下问题不阻断当前使用，但后续继续开发时应优先检查：

1. 公开的 `GET /api/big-stack` 当前返回内部 `playerId`、`note`、`updatedAt` 等完整字段。现有 805 条记录的备注均为空，没有实际隐私数据；在拆分公开 DTO 前，不要在备注中写手机号或其他敏感信息。
2. 修改历史中的 `points_awarded = 1` 目前只是 PB 审计标记，尚未写入任何真实积分账户。后台会显示“PB积分 +1”，但这不代表积分已到账。后续应在“接入积分台账”和“移除积分文案”之间明确选择一种。
3. 大堆单条编辑没有使用 `updatedAt` 做乐观锁。两个管理员同时编辑同一条记录时，后保存者会覆盖先保存者；可复用普通周赛成绩的 `expectedVersion` 冲突保护方案。
4. 494 条未绑定记录是按产品要求保留的正常状态：只做周赛选手 ID、WCA ID 或唯一完全同名匹配，不做模糊匹配。管理员可在后台逐条补绑定。
5. 全量基线导入会在事务中替换该项目当前榜单，但删除旧榜单时没有逐条写入“被替换前”快照。重要全量替换前仍应保留数据库或运行目录备份。
6. Docker 生产环境的 `/app/data` 来自服务器持久卷。命令行执行 `npm run big-stack:baseline` 前，应确认服务器的 `/opt/ln-cubing/data/big-stack-baseline.json` 已同步到最新仓库版本；后台上传 Excel 不受这一点影响。

目前没有必须紧急修复的上线阻断问题。核心逻辑仍以“每个项目、每位选手只保留一个长期最高成绩”为准。
