# 周赛系统审查（2026-10-08）

## 范围与结论

检查当前周赛首页、历史详情、移动端样式、成绩查询/录入/修订、Excel 导入与回滚、PB 更新、管理员认证和游客读权限。使用线上公开数据做浏览器验证；没有提交测试成绩、修改线上选手档案或试探管理员密码。

原截图含旧版本的重复名次及周赛编号。当前线上首页总排名已经正常，但移动端的主要成绩在屏幕外、滚动时菜单层级以及多处成绩展示逻辑仍需要修正。这是定向代码审查和功能验证，不代表完成了全部安全渗透测试。

## 本轮修复

1. **手机成绩表的阅读顺序**：改为排名、姓名、平均/最终数量在前；固定排名和姓名以便横向对照，提供滚动提示。移除依赖旧列序号的宽度规则，改用语义列宽，兼容常规项目、大堆及管理员操作列。
2. **顶部菜单遮挡**：提高固定页头的层级，避免周赛菜单文字滚动到页头上方；手机品牌和菜单同排。下拉列表限制高度，并允许列表内部滚动。
3. **切换项目的请求竞态**：取消旧成绩请求；旧请求完成、失败或结束时均不能覆盖新请求的状态。切换周赛/项目/赛制时清空旧列表，避免暂时把上一项目成绩展示在新标题下。
4. **游客姓名候选缺失**：从当前成绩中的选手生成搜索候选，无须访问管理员选手搜索接口。
5. **历史与实时榜单名次不一致**：历史详情按成绩重新排序并生成名次；平均相同时使用本轮最好单次，避免历史 PB 影响本轮顺序。实时接口的组内名次重新计算，避免导入源名次影响筛选和导出。
6. **个人 PB 被本周最好替代**：实时成绩增加选手档案 PB，展示优先使用档案 PB，缺失时使用导入源 PB 和本轮最好作兼容回退。保留源文件值，不修改历史记录。

7. **北京时间和首次渲染不一致**：隐藏录入区在服务端和浏览器按各自时区格式化周赛时间，导致 React 首次渲染内容不一致。统一使用 Asia/Shanghai，缺失日期使用稳定标签；操作日志也固定使用北京时间。

## 已验证的保护

- 匿名访问选手档案、修订日志、WCA 匹配候选和管理员选手搜索接口均返回 401；内部测试周赛成绩返回 404。
- 已检查的成绩写入、修订、删除和导入提交/回滚接口要求周赛管理员认证，并检查请求来源。
- 新成绩计算、尝试记录、PB 刷新及重排名使用数据库事务；选手同周同项目成绩有唯一索引，防止重复录入。
- 导入提交重新检查赛制、选手状态及已有成绩；回滚检查结果是否后来被修订，避免直接删除修订后的成绩。

## 仍需处理的设计风险

### 优先级 1：多人修订会覆盖先前修改

成绩修订接口仅接收 attempts、format、reason；没有客户端读取时的版本号或 updated_at。数据库行锁保证写入串行，但不能判断用户正在修改的是过期页面。两个管理员同时打开同一成绩，后保存者仍可能覆盖先保存者的修改。

建议：修订与删除提交 expectedUpdatedAt；数据库条件更新或锁定后对比版本，冲突返回 409 并要求刷新。需同时修改接口、录入界面和导入回滚的版本约定，并用两并发客户端验证。本轮没有改变该协议。

### 优先级 2：操作日志不能区分实际管理员

当前使用共享管理员密码；导入日志的 actor 为固定 weekly-admin，手工成绩修订记录没有实际账号身份。可以知道变化和原因，但不能定位实际操作人。

建议：在需要多人协作时采用独立管理员账号，在会话中存放管理员 ID，并记录到修订与导入日志。该项涉及账号与数据库结构，尚未实施。

### 优先级 2：登录限流为进程内状态

weekly-login-rate-limit 使用内存 Map。服务重启会清空，多个实例之间不共享；未启用可信代理配置时所有用户共用一个限流桶。扩大实例或出现频繁登录失败时，既可能限流失效，也可能影响其他管理员。

建议：使用数据库或 Redis 保存按可信客户端 IP/账号统计的限流状态；先确认 Nginx 清洗代理头，再启用逐客户端限流。没有通过线上错误密码请求验证，以免锁定真实管理员。

### 优先级 2：并列规则尚未统一

周赛实时/历史榜单目前按平均、本轮最好、姓名排列，并生成连续名次；省榜使用相同平均并列、跳号的 RANK 规则。两个榜单可以有不同规则，但页面应明确解释。若周赛也要完全同分并列，需要统一计算、导出及回归测试；本轮延续当前连续名次规则。

### 优先级 2：PB 标记与历史时点含义需明确

成绩修订会重建档案 PB，并把被修订成绩的 PB 标记清零；其他历史成绩的 PB 标记并非按时间顺序全部重算。档案中的当前 PB 与“该周当时刷新 PB”的徽标并非同一含义。

建议：明确徽标表示录入时刷新、比赛日期时刷新或当前保持的 PB，再统一修订/回滚后的徽标计算。本轮修复 PB 数值展示，没有重写历史徽标。
